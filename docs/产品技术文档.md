# 轻音播放 · 产品技术文档

| 项目 | 内容 |
| --- | --- |
| 版本 | v0.1（MVP 规划） |
| 状态 | M0 技术验证已通过（见 [M0 技术验证结果](M0-技术验证.md)），可进入 M1 |
| 形态 | 纯 Web 应用（可安装为 PWA） |

---

## 1. 项目概述

**定位**：一个跑在浏览器里的本地音乐播放器。用户指向自己的音乐文件夹即可播放，零安装、零上传、不依赖任何在线服务。

**目标**：先做到"自己能天天用起来"——打开就有库，点一下就能放，关掉再打开一切还在。

**非目标**：在线音源、账号体系、曲库管理工具、社交分享。这些都不属于 MVP。

## 2. 产品定位与边界

- **音源**：仅本地文件。不上传、不联网解析、不抓取封面歌词。
- **平台**：Chromium 系（Chrome / Edge）为主支持，其他浏览器降级可用。
- **库规模假设**：数千首量级；超过此量级优先保证不卡 UI，而非极致性能。
- **核心使用流程**：
  选择文件夹 → 扫描入库 → 浏览与搜索 → 双击播放 → 控制与切歌 → 下次打开自动恢复

## 3. 主要功能（MVP）

### A. 曲库接入

1. **文件夹选择** —— 主路 `showDirectoryPicker()`（Chromium），回退路 `<input webkitdirectory>`（全浏览器，但刷新即失效）。两条路统一抽象为 `MusicSource` 接口。
2. **递归扫描与元数据解析** —— 读取标题、艺术家、专辑、时长、内嵌封面。
3. **增量缓存** —— 解析结果存入 IndexedDB，缓存键为 `路径 + 文件大小 + 修改时间`，重开页面只解析变化过的文件。
4. **格式兼容标记** —— APE / WavPack / DSD 浏览器无法解码，明确标记为"不支持"而非静默失败。

### B. 浏览与检索

5. **曲目列表** —— 平铺列表，支持搜索与排序。中文排序使用 `Intl.Collator('zh-Hans-CN', { numeric: true })`。

### C. 播放

6. **播放内核** —— 播放 / 暂停、上一首 / 下一首、拖动进度、音量调节。
7. **播放模式** —— 顺序 / 单曲循环 / 列表循环 / 随机。随机采用洗牌，避免重复播同一首。
8. **播放队列** —— 双击某首即从该处顺序播放，队列可见、可增删。
9. **键盘快捷键** —— 空格播放暂停、方向键切歌与快进快退。

### D. 体验与持久化

10. **状态持久化** —— 音量、当前曲目与播放进度、播放模式、目录句柄、曲库缓存。
11. **系统媒体集成** —— 接入 MediaSession API，支持系统媒体键与锁屏 / 控制中心展示。
12. **PWA** —— Service Worker 缓存应用外壳，可安装到桌面，具备原生应用观感。

## 4. MVP 范围外

在线音源与账号登录、歌词（含在线抓取与逐字同步）、音效 / 均衡器 / 频谱可视化、元数据编辑与自动整理文件夹、多端同步、社交分享、主题皮肤系统、移动端适配。

这些功能每一项都足以单独消耗大量工期，且都不能帮助验证"核心播放体验是否成立"。

## 5. 技术方案

### 5.1 技术栈

| 用途 | 选型 |
| --- | --- |
| 构建 | Vite |
| 语言 | TypeScript |
| UI | React |
| 状态 | Zustand |
| 存储 | IndexedDB（`idb` 封装） |
| 元数据 | `music-metadata`（`parseBlob`） |
| 测试 | Vitest + Testing Library |

### 5.2 架构分层

```
src/core/      纯逻辑：队列、模式推进、洗牌、排序搜索、时长格式化 —— 全部可单测
src/platform/  浏览器 API 适配：文件句柄、IndexedDB、音频元素 —— 以接口包住
src/ui/        界面组件
```

分层的核心目的是**让音频与 DOM 之外的逻辑可测**：`core` 不引用任何浏览器 API，`platform` 通过接口注入，测试时替换为假实现。

### 5.3 数据存储

统一使用 IndexedDB，承载三类数据：

- **曲库缓存**：曲目元数据与封面，键为 `路径 + 大小 + 修改时间`
- **目录句柄**：用于重开页面后免于重新选目录
- **播放状态**：音量、当前曲目、播放进度、播放模式

不使用 localStorage：条码句柄与结构化数据均超出其能力范围，且同步 API 会阻塞主线程。

### 5.4 平台约束

| 约束 | 应对 |
| --- | --- |
| 浏览器无法自动扫盘，只能由用户授权目录 | 目录选择作为显式入口，句柄持久化以减少重复操作 |
| 句柄持久化后仍需一次点击重新授权 | 设计为"一键恢复曲库"，不承诺全自动加载 |
| 解码能力受限于 Chromium | 支持 mp3 / flac / m4a / ogg / wav；其余格式标记为不支持 |
| 解析为 CPU 密集操作，单线程会卡 UI | Web Worker + 分片处理，扫描过程显示进度 |

## 6. 测试与质量

- **单元测试**：覆盖 `core` 全部纯逻辑——目录树遍历、元数据映射、四种模式下的上下一首计算、洗牌、时长格式化、中文排序与搜索。
- **可测性设计**：`MusicSource` 以接口形式注入，扫描与入库逻辑可在 jsdom 中测试，无需真实浏览器 API。
- **手动冒烟清单**：保留约 10 条无法自动化的检查项（真实出声、进度恢复、媒体键响应等），交付前逐条执行。
- **变更纪律**：每次改动均创建 commit；每次改动同步编写或更新测试，并确保全部通过后再交付。

## 8. 风险与待验证项

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 元数据解析方案 | ~~`music-metadata` 的浏览器可用性与打包体积尚未验证~~ **M0 已消解**：浏览器产物无 `node:` 依赖，JS 合计 444KB（主 chunk gzip 49.5KB，且解析器按格式拆分）；无需自研解析器 | 已确认，见 [M0 技术验证结果](M0-技术验证.md) |
| 中文标签乱码 | 早期 mp3 标签常用 GBK 编码，易读成乱码 | **M0 未覆盖**，仍需在元数据层预留编码回退逻辑 |
| 大库扫描卡顿 | ~~数千文件解析耗时可观~~ **M0 已大幅降低**：瓶颈是 I/O 而非 CPU，`parseFile` 解析 31MB 文件仅 2.3ms；默认只读文件头（512KB）即可拿到标签与时长 | 先只读文件头，读不出标签时再回退读整文件 |
| 授权体验 | 每次会话需一次点击确认目录权限 | 明确交互提示，避免用户误以为曲库丢失 |
