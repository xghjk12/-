# 交接文档（给接手的 Agent）

> 这份文档是写给**接手的 Agent** 的，不是给最终用户的。目标是让你在 10 分钟内能跑起来、
> 知道哪些东西不能动、哪些问题已经讨论过不要再翻案。
> 产品/技术设计的细节在 [`产品技术文档.md`](产品技术文档.md) 与 [`技术方案.md`](技术方案.md)，
> 这里只写"接手必须知道"的部分。

## 1. 这是什么

「轻音播放」——跑在浏览器里的本地音乐播放器（PWA）。指向自己的音乐文件夹即可播放，
零安装、零上传、不联网解析。曲库元数据存 IndexedDB 并做增量缓存，几千首可用。

- 仓库：https://github.com/xghjk12/- ・分支 `main`
- 技术栈：Vite + React 19 + TypeScript（strict）+ Zustand + `idb` + `music-metadata`
- 验证：Vitest 单测 422 项、demo 37 项、Playwright 界面冒烟、3000 首基准

## 2. 三分钟跑起来

```bash
git clone https://github.com/xghjk12/- qingyin-player
cd qingyin-player
pnpm install
pnpm dev            # 开发服务器
pnpm verify         # typecheck + 单测 + demo + 静态一致性 + 产物检查（交付前必跑）
```

界面相关改动额外跑 `pnpm check:ui`（用本机已装的 Edge 驱动，不需要下载 Chromium）；
改到扫描/缓存/性能时跑 `pnpm bench`（3000 首真实文件）。

`?selftest=1` 打开内置自检（核心逻辑在浏览器里逐项验证），`pnpm check:ui` 会读这张表。

## 3. 不变量：这些不要破坏

| 约束 | 为什么 / 怎么保证 |
| --- | --- |
| 依赖方向 `ui → platform → core`，`core` 里**禁止任何平台 API** | 有测试强制（`src/core/no-platform-api.test.ts`）。它让 `core` 的 246 项单测不碰浏览器，也是将来换 UI 框架/上桌面端的前提 |
| **进度与当前歌词行不进 React state** | 播放位置每秒变，进 state 会带着曲目列表重渲染。用 rAF 直读引擎、只在行号变化时 setState（歌词面板与迷你歌词各自做） |
| 曲目身份 = `path`；缓存键 = `path\0size\0mtime` | **刻意分开**：改标签不该让播放状态/歌词丢失，但改了文件就得重解析 |
| 歌词记录键 = 曲目 `path`；`import`/`paste` 优先于扫描认领 | 见 `platform/lyricSync.ts` 的三条规则，有 14 项单测钉着 |
| 扫描 `phase` 有 `lyrics` 一档，别在它之前报 `done` | 歌词认领在音频扫描之后；提前报 done 会让界面/脚本读到空歌词（踩过） |
| PWA 用 `registerType: 'prompt'`，**不要改回 `autoUpdate`** | 静默换外壳会让用户一直停在旧版本且毫无提示（踩过） |
| 「去搜歌词」只拼 URL 交给浏览器，**应用不请求不解析任何第三方内容** | 产品取舍线的核心，见 `技术方案` 13.1 |
| 歧义不猜：一个 `.lrc` 命中多首、多首命中一个 `.lrc` 都不自动认领 | 猜错歌词比没有歌词更糟。内置样本就是"同一首歌两种格式"的歧义用例 |
| 纯音乐占位识别为"没有歌词"；署名行标记但不删除 | 来自真实下载文件的反向补丁，见 `技术方案` 13.4 |

## 4. 已经定过的决定（不要重新论证）

1. **不做应用内抓取歌词**。实测 `api.lrc.cx` 不给任何 `Access-Control-*` 响应头，纯前端被浏览器拦死；
   绕过就要加代理服务器，产品形态会变。替代方案已落地：外部批处理工具产出**与音频同名**的 `.lrc`，
   播放器扫描时自动认领（`README.md` 有完整命令，`技术方案` 13.8 有 22 首全量实测）。
2. **逐字歌词不做**：增强型 LRC 的逐字时间**已经解析进 `LyricLine.words`**，但界面只按行高亮。
   要升级时不用重新解析。
3. **不做在线音源、账号、元数据编辑、音效、移动端**（`产品技术文档` 4 节）。
4. **桌面端：尚未开工**，已论证到"Electron 可行、Tauri 被环境排除"（见第 6 节），别从头推演一遍。

## 5. 已知欠账

完整清单在 [`技术方案.md`](技术方案.md) **第 14 节**，每条都写了"什么时候该动它"。摘要：

- **曲目身份仍是 `path`**：要支持第二个音乐目录/NAS 时必须改成 `sourceId:path`（迁移机制已就绪：
  IndexedDB v2 + `storage.test.ts` 里的 v1→v2 升级用例）。**越晚改越贵。**
- `showDirectoryPicker`（句柄路径）的扫描成本从未实测（自动化驱动不了原生弹窗），只有手动清单。
- 播放列表 / m3u、封面、多库、无障碍审计：都未做，触发条件见第 14 节。

## 6. 未完成的线索（接手时最可能有用的部分）

1. **桌面端（用户明确想要，但还没开始）**
   - 目标只有一条：**关掉窗口继续放歌 + 托盘 + 开机自启**。独立窗口/桌面图标/离线这些 PWA 已经有了。
   - 选型实测结论：**Electron 可行**（`registry.npmjs.org` 通；Electron 二进制在 GitHub Releases，
     本机需 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 与
     `ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/`）；
     **Tauri 排除**（本机无 Rust、无 MSVC/VS Build Tools，Windows 链接需要它）。
   - 建议的第一步是**半天探路**，不要直接开做：① 拉得起 Electron；② **定死 origin 方案**
     （内部 http 服务必须**固定端口**，否则 IndexedDB 的 origin 每次变，用户数据会"凭空清空"；
     或注册 `app://` 自定义协议并声明 standard+secure）；③ `nodeMusicSource`（已存在且有 5 项单测）
     接到主进程后，真实曲库能扫能放。
   - 已知代价：切到桌面端后 **PWA 那部分冒烟断言不适用**，托盘/自启/关窗继续放**自动化不了**，
     只能人工清单——桌面端是"多一个验证更弱的分支"，不是"同一产品加个壳"。
2. **仓库名是 `-`**（`github.com/xghjk12/-`），像是创建时名字被吞了。要改的话在 GitHub 设置里改名，
   本地 `git remote set-url` 跟着改。
3. **文档里有本机痕迹**：`README.md` 的歌词工作流章节有 `D:\轻音播放\新建文件夹`，
   `技术方案` 13.8 的实测表里有用户的歌名。用户还没决定是否清理；要清就得改历史（force push），
   趁仓库还新、无人 clone 时做最干净。
4. **没有 LICENSE 文件**。公开仓库建议补一个（用户倾向 MIT，未确认）。

## 7. 本机环境的坑（在这台机器上干活才会遇到）

- **git 不在 PATH**：`%LOCALAPPDATA%\GitHubDesktop\app-3.6.3\resources\app\git\cmd\git.exe`。
- **GitHub 域名被 Steam++（Watt Toolkit）加速器接管**：hosts 把二十多个 GitHub 域名指向 `127.0.0.1`，
  加速器在 `0.0.0.0:443` 监听并转发。注意这不是"屏蔽"而是"加速"：**直连 GitHub 的真实 IP 实测不通**
  （四个 IP 的 443 全部失败），所以必须让流量走加速器，别去改 hosts。
  副作用：`web_fetch` 这类拒绝非公网地址的工具打不开 GitHub；读仓库内容可走
  `https://cdn.jsdelivr.net/gh/<owner>/<repo>@main/<path>`。
- **推送鉴权**：GCM（`credential.helper manager`）里没有存 token 时，从**无 TTY 的进程**发起 `git push`
  会在 `could not read Username` 处失败（GCM 的图形窗口起来了也接不上）。可靠的两种做法：
  让用户在**真实终端**里跑一次 `git push`，或用 **GitHub Desktop** 的 Push 按钮（它有自己的凭据）。
  一旦成功过一次，GCM 会存住，之后无 TTY 也能推。
- **受限沙箱下 `pnpm test` 会失败**（vite 内部 `exec("net use")` → `spawn EPERM`）。
  绕过：`node node_modules/vitest/vitest.mjs run --pool=threads`。全权限环境无此问题。
- **提交信息含中文/引号时**：写成文件后 `git commit -F <文件>`，别在 PowerShell 里直接 `-m`。

## 8. 和这位用户协作的偏好

- 中文交流；他给的是**短指令**（"先稳"/"顺手"/"路线一"/"跑一遍"），需要你先把选项摆清楚再让他选。
- 重视**实测而不是推测**：功能可行性、性能、CORS 这类问题，他会接受"我测了，结论是 X"，
  但不接受"应该可以"。写文档时把实测数字带上。
- 每次改动都要 **git commit + 补测试 + 全绿再交付**（`AGENTS.md` 也是这么写的）。
- 不喜欢过度设计：宁可先做小切口验证，也不要一次铺开。
- 出了问题他要的是**根因 + 修复 + 怎么防止再犯**，不是"已修复"三个字。
