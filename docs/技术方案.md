## 2. 技术选型

### 2.1 选定方案

| 用途 | 选型 | 状态 |
| --- | --- | --- |
| 构建 | Vite | ✅ |
| 语言 | TypeScript（`strict` + `verbatimModuleSyntax`） | ✅ |
| UI | React | ✅ |
| 状态 | Zustand | ✅ |
| 元数据 | `music-metadata` | ✅ |
| 存储 | IndexedDB（`idb` 封装） | ✅ |
| 测试 | Vitest（`core` + `platform` + `ui/playback`） | ✅ |
| 界面冒烟 | `playwright-core` + 本机 Edge（见 9.1） | ✅ |
| PWA | `vite-plugin-pwa` | ✅ |

### 2.2 结论：不上 Electron

产品文档原本就写了"纯 Web 应用（可安装为 PWA）"，M0 之后这个结论更强了：**Electron 的主要收益对本产品不成立**。

| 通常用 Electron 换来的东西 | 对本产品是否成立 |
| --- | --- |
| 支持 APE / DSD / ALAC 等 Chromium 解不了的格式 | ❌ 曲库是 flac + mp3，两者 Chromium 原生解码，一行解码代码都不用写 |
| 免去目录授权 | ⚠️ 仅省一次点击，不值 100MB 安装包 |
| 更快的扫描 | ❌ 实测瓶颈是每文件的 I/O，且只读 16KB 就够；Electron 不会更快 |
| 打包分发方便 | ❌ 恰好相反：未签名 exe 会触发 SmartScreen，给朋友试的门槛更高 |

**重新评估的触发条件**（满足任意一条再切，届时成本很低）：

1. 曲库里开始出现 **APE / DSD / ALAC**（`.m4a` 里装 ALAC 最容易被忽略）
2. 需要文件夹监听、开机自启、托盘常驻
3. 需要比特完美 / 独占输出

第 3.2 节的依赖方向保证了切换代价：届时只增加一个 `platform/desktop` 适配层，`core` 与 `ui` 不需要改。

## 3. 架构与依赖方向

### 3.1 分层

```
src/core/        纯逻辑：格式判定、缓存键、元数据区计算、标签编码、队列与模式、排序搜索
src/platform/    平台适配：字节读取、曲库来源、元数据解析、IndexedDB、音频元素、MediaSession
src/ui/          React 组件 + Zustand store
```

### 3.2 依赖方向（硬约束）

```
ui  ──▶  platform  ──▶  core
                          ▲
                          └── 不依赖任何东西
```

**`core` 里不允许出现 `window` / `document` / `navigator` / `indexedDB` / `node:` / `require(`。**

这条纪律是整个方案的地基：它让"音频与 DOM 之外的逻辑"可以 100% 单测，也让将来上 Electron 或换 UI 框架不用重写业务逻辑。M0 已经按这条走（`core` 里的 24 项测试全部不碰平台 API）。

**用测试强制，而不是靠自觉**：⬜ M1 增加 `src/core/no-platform-api.test.ts`，扫描 `src/core/` 下的非测试文件，命中上述关键字即失败。

## 4. 核心模块设计

### 4.1 元数据解析：三级读取策略 ⬜（M1 从两级升级）

M0 实测的核心结论：**解析耗时与读多少字节无关**（8KB 到 512KB 都是 0.5ms 左右），成本纯粹在磁盘 I/O；而真实文件的元数据区只有 **8.6KB（FLAC）/ 351B（MP3）**。当前实现固定读 512KB，是所需量的几十倍，却又**不能保证**覆盖超大内嵌封面。

因此改成按容器结构算准范围：

| 级别 | 读什么 | 何时用 | 实测依据 |
| --- | --- | --- | --- |
| L1 探测 | 前 16KB | 总是先做。同时用于算出元数据区 | 覆盖绝大多数文件；16KB 也够 MP3 的第一个 MPEG 帧（读时长要用 Xing 头） |
| L2 精确区 | `[0, metadataRegionEnd)` | 元数据区大于探测长度时。**只多读这一块** | FLAC 走 metadata block 头；ID3v2 头 10 字节里就有标签长度 |
| L3 全文件 | 整个文件 | L1/L2 都没读出标题/艺术家/专辑时 | 兜住标签只在文件尾部的情况（只有 ID3v1 的老 mp3） |

`metadataRegion.ts` 要实现的纯逻辑：

- **FLAC**：以 `fLaC` 开头时，从偏移 4 开始逐个读 metadata block 头（每块 4 字节：1 字节「是否最后一块 + 类型」+ 3 字节长度），累加到最后一个块即为元数据区结束位置。块头本身不足 4 字节时返回 `undefined`（交给上层回退）
- **MP3**：以 `ID3` 开头时，长度是第 6–9 字节的 syncsafe 整数（每字节只用低 7 位）；v2.4 若置了 footer 标志再 +10
- **其它容器**：返回 `undefined`，上层回退到固定上限

这样同时解决两件事：常见文件的 I/O 降到几十分之一，超大封面也不会再被静默漏掉。

### 4.2 格式判定：两档 + codec 复核 ✅

M0 的意外发现是 `music-metadata` 支持的格式远多于 Chromium 能解码的格式——**APE / DSD / WavPack 读得出标签但放不出声音**；同时它对损坏文件抛的是 `EndOfStreamError` 这类底层错误，**没有干净的"不支持"信号**。

所以判定必须由我们自己给出，分两档：

| 档位 | 含义 | 界面表现 |
| --- | --- | --- |
| `decodable` | Chromium 能解码 | 正常播放 |
| `metadata-only` | 能读标签，不能播放 | 展示标题艺术家，播放按钮禁用并给出说明 |

两个细节：

- `.m4a` / `.mp4` 标记为 `codecSensitive`，解析出 `format.codec` 之后再用 `resolveVerdict` 复核一次——容器里装 ALAC 时要降级
- 解析失败不抛异常，失败原因进 `parseError` 并回退文件名标题，**一个坏文件不中断整次扫描**

### 4.3 GBK 标签回退 ⬜

产品文档 8 节里唯一还没被 M0 触及的风险。老 mp3 常见做法是 ID3v2 的编码字节写 `0x00`（声明 ISO-8859-1）却塞进 GBK 字节，`music-metadata` 会按 latin1 解成乱码。

`tagEncoding.ts` 的处理方式：

1. 识别特征：字符串里出现大量 U+0080–U+00FF 区间的字符（latin1 解码字节的典型形态）
2. 把每个码位还原成 1 个字节（latin1 编码回去）
3. 用 `TextDecoder('gbk')` 重解码；只有在结果包含 CJK 字符且不含替换字符 `U+FFFD` 时才采用

Node 与 Chromium 都支持 `TextDecoder('gbk')`，所以这段逻辑既是 `core` 纯逻辑（解码器以参数注入），也能在浏览器里原样运行。

> 注意：GBK **无法**可靠地反推，所以判定必须保守——宁可保留乱码也不要错改成另一种乱码。

### 4.4 曲库来源抽象 ✅ 接口 / 🔬 浏览器实现

产品文档 3.A.1 要求 `showDirectoryPicker()` 与 `<input webkitdirectory>` 统一成一个接口：

```ts
interface MusicSource {
  readonly rootName: string;
  listAudioFiles(onProgress?: (found: number) => void): Promise<AudioFileRef[]>;
  open(ref: AudioFileRef): Promise<ByteSource>;
}
```

- 主路 `showDirectoryPicker()`：句柄可持久化
- 回退路 `<input webkitdirectory>`：用 `webkitRelativePath` 作相对路径，刷新即失效
- Node 实现 ✅：测试与命令行冒烟用，与浏览器侧共用同一套 `core` 判定

浏览器实现目前是 M0 的验证形态（`m0/browserMusicSource.ts`），M1 正式并入 `src/platform`。

### 4.5 播放队列与模式 ⬜

放 `core/queue.ts`，纯逻辑、可穷举单测（接口与行为已在 `demo/core.js` 里跑通过，直接迁移）：

- 四种模式：顺序 / 列表循环 / 单曲循环 / 随机
- **单曲循环只在自然播放结束时重复本首，手动点「下一首」仍前进**——靠区分 `ended` 事件与显式指令实现，这是最容易写错的一处
- 随机用洗牌而不是每次随机取，避免连续重复；切到随机时重新洗牌
- 顺序播放走到末尾停止并提示，不静默绕回

## 5. 数据存储

### 5.1 曲目身份 vs 缓存键（重要区分）

两者用途不同，混用会出 bug：

| 概念 | 键 | 用途 | 可变性 |
| --- | --- | --- | --- |
| **曲目身份** | `path`（相对路径，posix） | 播放状态、队列引用 | 文件内容变了也不变 |
| **缓存键** | `path + 大小 + 修改时间` | 元数据缓存失效 | 文件一变就变 |

如果拿缓存键当曲目身份，文件一被编辑（时间戳变化）「上次播到哪儿」就丢了。

### 5.2 IndexedDB schema ⬜

| 对象仓库 | 键 | 值 | 说明 |
| --- | --- | --- | --- |
| `files` | `path` | `{ path, size, lastModified, cacheKey }` | 目录清单，增量对比用 |
| `tracks` | `cacheKey` | `TrackRecord` | 元数据缓存 |
| `covers` | `cacheKey` | `{ mimeType, data: Blob }` | **封面单独存**，列表渲染时不必把所有封面读进内存 |
| `state` | 固定键 | `{ volume, mode, trackPath, positionSec }` | 播放状态 |
| `handles` | `sourceId` | `FileSystemDirectoryHandle` | 目录句柄（结构克隆，`localStorage` 存不了） |

不用 `localStorage`：句柄与结构化数据都超出其能力，且同步 API 会阻塞主线程。

### 5.3 增量扫描算法 ⬜

```
对扫描到的每个音频文件 f：
  prev = files.get(f.path)
  if prev 存在 且 prev.cacheKey === cacheKey(f):
      命中 → 直接复用 tracks.get(prev.cacheKey)，完全不用读文件
  else:
      解析元数据 → 写 tracks[cacheKey] 与 covers[cacheKey] → 更新 files[f.path]
扫描结束后：
  对 files 里存在但本次没出现的 path → 删除该条与其 tracks / covers（文件已删除或改名）
  对没有 files 引用的 tracks / covers → 一并清理（避免缓存无限增长）
```

最后两步（清理孤儿）最容易被忽略，不做的后果是缓存只增不减。

### 5.4 封面内存管理 ⬜

3000 首的库不能把封面都留在内存里：

- 列表按需从 `covers` 读，`URL.createObjectURL` 之后**必须在滚出视口或组件卸载时 `revokeObjectURL`**，否则内存只增不减
- 用一个小的 LRU（约 100 张）兜住来回滚动
- 无封面是常态：实测两首真实歌曲都没有内嵌封面，界面必须有稳定的占位样式，不能出现空框

## 6. 扫描调度与性能预算

### 6.1 修正产品文档 5.4 节的假设

产品文档写的是「解析为 CPU 密集操作，单线程会卡 UI → Web Worker + 分片处理」。M0 实测推翻了前半句：

- 稳态解析 **0.5–0.8ms/首**，3000 首合计约 2s CPU，本身不构成卡顿
- 成本在 I/O，而 I/O 是**异步**的，`Blob.slice().arrayBuffer()` 不阻塞主线程
- 真正需要的是**让出事件循环**（每处理 N 个文件 `await` 一次），而不是另开线程

**决定：先单线程 + 异步分片，不引入 Web Worker。**

> **Worker 的触发条件（已按实测重写）**
>
> 原文写的是「实测发现卡顿时再上 Worker」。3000 首实测（见 6.2）显示这个条件**永远不会触发**：
> 首次扫描 9.4s / 3000 首，而且这 9.4s 里主线程一直在让出（每 25 个文件一次），滚动与点击都不受影响。
> 「解析慢」不再是引入 Worker 的理由。
>
> 真正会重新触发它的是**需要在一瞬间完成大量同步计算**的场景，目前只有一个候选：
> 给曲库建本地检索索引（拼音、分词、模糊匹配）。那是纯 CPU、且必须在用户开始输入之前算完，
> 才值得搬到 Worker 里。届时的迁移成本已经被分层压到最低：`core` 不依赖任何平台 API，
> 搬进 Worker 只涉及 `platform` 的调度。

> **M1 实现后的复测**（`M0_MUSIC_DIR='D:\轻音播放\新建文件夹' pnpm test`，两首真实歌曲 25.8MB）：
> 遍历 1ms；**只读文件头 2/2**，实际读取 **0.0MB（占总体积 0.1%）**；疑似乱码标题 0。
> 三级读取把「只读文件头」从「读 512KB 猜得够不够」变成「按容器算准后精确读取」，
> 同时补上了原来的漏洞：封面块排在探测窗口之后时不再被静默漏掉（见 `metadata.test.ts` 的 L2 用例）。

### 6.2 性能预算

以 3000 首 flac + mp3 为目标（对应产品文档 2 节的库规模假设）：

| 指标 | 预算 | 依据 | 3000 首实测（`pnpm bench`） |
| --- | --- | --- | --- |
| 单文件 I/O | ≈ 16KB | L1 探测；实测真实元数据区 8.6KB / 351B | ✅ 15.5KB/首（合计 46.4MB） |
| 首次扫描 I/O 总量 | < 50MB | 3000 × 16KB | ✅ 46.4MB |
| 首次扫描总时长 | < 30s | I/O + 解析 + 入库 | ✅ **9.4s**（逐文件处理 8.8s、列出来源 0.6s） |
| 二次打开（全缓存命中） | < 500ms | 只读 IndexedDB，完全不碰音频文件 | ✅ **241ms** 刷新到列表可见 |
| 列表渲染 | 不随曲目数退化 | 必须虚拟化，见第 7 节 | ✅ DOM 恒定 27 行、滚动 60fps |
| —— | —— | —— | JS 堆 12MB |

实测把两条**原本的担心变成了不成立**，也纠正了一处猜测：

- **"3000 个 File 对象会吃内存"**：不成立。File 是轻量句柄，3000 首下 JS 堆只有 12MB。
- **"二次打开要重新遍历目录、可能好几秒"**：实测全命中重扫 2.5s，但**刷新到可见只有 241ms**
  （纯读 IndexedDB），所以"打开就有库"这条目标是达标的；2.5s 只发生在用户主动触发扫描时。
- **"重扫慢是因为把 3000 条元数据从 IndexedDB 读出来"**：猜错了。分项计时显示读元数据缓存只花 41ms，
  **1.58s 花在"列出来源"**——逐文件读 `name` / `size` / `lastModified` 每读一个属性都是一次
  浏览器进程往返（File 是句柄，不是 JS 值）。这条只影响主动重扫，暂不优化。

> **口径与未覆盖项**：`pnpm bench` 走的是 `<input webkitdirectory>` 这条路——Playwright 能给
> 这种输入直接喂一个目录，而 `showDirectoryPicker()` 需要真人手势与原生弹窗，自动化驱动不了。
> 因此**句柄那条路的「每文件一次 `getFile()`」开销没有被量到**（它同样是进程往返 + 一次系统调用，
> 只会更慢）。这条留在手动清单里：见第 9.1 节末。

### 6.3 扫描交互

- 进度显示已发现/已解析文件数，扫描可取消
- IndexedDB 写入按批（每 N 个文件一个事务），逐条写事务开销会吃掉收益
- 遇到无法解码的格式不报错、不中断，标记后继续（产品文档 3.A.4 的要求）

## 7. 界面层 ⬜

### 7.1 列表必须虚拟化

产品文档的库规模假设是"数千首"。3000 个 DOM 行的平铺列表会明显卡顿，**虚拟化是 M1 的必要项而不是优化项**：只渲染视口内的行（外加少量缓冲）。

选型倾向：先手写一个最小的窗口化实现（固定行高，约 50 行代码），避免为单一场景引入依赖；如果后续需要可变行高或分组再考虑 `@tanstack/react-virtual`。

### 7.2 状态管理边界

| 数据 | 存放位置 | 理由 |
| --- | --- | --- |
| 曲库列表、当前曲目、音量、播放模式 | Zustand | 低频变化，需要驱动 UI |
| **播放进度（每秒数次）** | 不进 React state | 用 rAF 直接改 DOM 的 `style.width` / `textContent`，否则整棵列表跟着重渲染 |
| 搜索输入 | 组件本地 + 防抖 | 高频，进全局 store 只会造成无谓广播 |

### 7.3 排序与检索

放 `core/sort.ts`，纯逻辑：

- 中文排序用 `Intl.Collator('zh-Hans-CN', { numeric: true })`，**collator 实例要复用**（构造开销不小，不能每次比较都建一个）
- 搜索对标题 / 艺术家 / 专辑做子串匹配，3000 行的过滤本身很快，不需要索引

## 8. 播放内核 ⬜

### 8.1 用 HTMLAudioElement 而不是 Web Audio

- `URL.createObjectURL(file)` 直接把本地文件交给 `<audio>`：**不会把整个文件读进内存**，拖动进度也不用自己实现
- 切歌时必须 `revokeObjectURL` 上一个对象 URL，否则每个听过的文件都会钉住一块内存
- Web Audio 只在将来要做均衡器 / 频谱 / 无缝衔接时才需要，属于 MVP 范围外（产品文档 4 节）

### 8.2 不支持格式的处理

播放前查 `resolveVerdict`：`metadata-only` 的曲目禁用播放并给出说明；随机 / 顺序推进时**自动跳到下一首可播放的曲目**（这个行为已在 `demo/` 里验证过，体验上比弹错误框好）。

### 8.3 系统媒体集成

MediaSession API（Chromium 原生支持）：

- `metadata`：标题 / 艺术家 / 专辑 / 封面
- `setActionHandler`：play / pause / prev / next / seekto
- `setPositionState`：让锁屏与控制中心显示正确进度

### 8.4 状态持久化的写入时机

播放进度不能每秒写一次 IndexedDB：

- 音量、播放模式：变化即写（低频）
- 当前曲目、进度：**暂停时、切歌时、以及每 5s 节流写一次**；页面 `visibilitychange` 隐藏时补一次

### 9.1 浏览器验证的边界

界面冒烟用 `playwright-core` + `channel: 'msedge'` 驱动本机已装的 Edge，**不下载 Chromium**（本机已有 Edge，`playwright-core` 本身不带浏览器）。它覆盖的是"跑得起来且没报错"这一层：页面加载、内置自检逐项通过、控制台无报错、截图留档。

它**不进 `pnpm verify`**，因为它依赖"本机装了 Edge"，属于开发机上的辅助验证，而 `verify` 要能在任何环境跑。

**明确不做**：

- 完整的视觉回归测试（截图基线比对）——版面还在频繁变动，维护基线是纯负担
- 交互链路的端到端测试——`showDirectoryPicker()` 需要真人手势，无法自动化；能自动化的那段（选择器之后的遍历与解析）本来就被 `platform` 契约测试覆盖了
- 追求覆盖率数字——`core` / `platform` 的价值在逻辑正确，界面的价值在能用，两者的验证手段本就不同

`core` / `platform` 的逻辑由单测兜住，界面由"冒烟 + 静态一致性检查 + 手动清单"三层兜住。交付前一律跑 `pnpm verify`，界面相关改动额外跑 `pnpm check:ui`，改到扫描/缓存/性能相关时跑 `pnpm bench`。

**手动清单里与性能有关的两条**（自动化覆盖不到，必须真人确认一次）：

1. **句柄路径的遍历开销**：`pnpm bench` 只能驱动 `<input webkitdirectory>`；`showDirectoryPicker()` 那条路
   每个文件要一次 `getFile()`，实测口径里没有它。用真实大库点一次「选择音乐文件夹」，
   看进度面板里的「遍历 x.xs」是否可接受。
2. **首次写入 IndexedDB 的耗时**：`pnpm bench` 里的曲库是同一份样本复制出来的，
   真实库的文件大小分布更散（几十 MB 的无损），首次扫描总时长要以真实库为准。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| GBK 老标签乱码 | 老 mp3 标题不可读 | 第 4.3 节的保守回退；判定不准时保留原样 |
| `.m4a` 里装 ALAC | 显示可播放但放不出声 | `codecSensitive` + 解析后 `resolveVerdict` 复核 |
| 超大内嵌封面 | 封面静默丢失 | 第 4.1 节的按容器精确读取 |
| IndexedDB 被浏览器清理 | 曲库缓存丢失 | 调用 `navigator.storage.persist()`；缓存不是用户数据，丢了只是重扫一遍 |
| 每次会话需重新授权目录 | 用户误以为曲库丢失 | 明确设计为「一键恢复曲库」，不承诺全自动加载 |
| 部分浏览器不支持目录选择 | Safari / Firefox 功能降级 | 回退到 `<input webkitdirectory>`，并在界面上说明"刷新后需重新选择" |
| 3000 行列表卡顿 | 界面不可用 | 虚拟化 + 封面 LRU + 进度不进 state（第 7 节） |
