## 1. 结论摘要

M0 要回答的是产品文档 7 节写的那句话：*`parseBlob` 能正确读出目标格式的标签与封面；目录递归遍历顺畅。失败则切换自研解析器方案。*

| # | 待验证问题 | 结论 |
| --- | --- | --- |
| 1 | `music-metadata` 能否读出 flac / mp3 的标题、艺术家、专辑、时长、内嵌封面 | ✅ 全部正确，含中文标签 |
| 2 | 浏览器侧能否用（打包、体积、有无 Node 依赖泄漏） | ✅ 可以，产物无 `node:` 引用 |
| 3 | 目录递归遍历是否顺畅 | ✅ 逻辑已验证（Node 侧同构实现 + 单测） |
| 4 | 是否需要回退到自研 ID3v2 / Vorbis comment 解析器 | ❌ 不需要 |
| 5 | 数千首规模会不会卡 | ✅ 主要手段是"只读文件头"，实测可行 |

**没有触发任何一条回退方案。**

## 2. 验证方法

### 2.1 测试样本

本机没有真实音乐文件，因此用 ffmpeg 生成了三个真实可解析的样本并提交进仓库，
测试直接读它们，`pnpm test` 不依赖本机是否装有 ffmpeg：

| 样本 | 内容 |
| --- | --- |
| `tests/fixtures/sample-cn.flac` | 2 秒音频，中文标签（青花瓷 / 周杰伦 / 我很忙）+ 内嵌 JPEG 封面 |
| `tests/fixtures/sample-cn.mp3` | 2 秒音频，同样标签，强制 ID3v2.3，带封面 |
| `tests/fixtures/plain.mp3` | 无任何标签，用于验证"标题回退到文件名" |
| `tests/fixtures/fake.ape` | 内容不是合法 APE，用于验证损坏文件不中断扫描 |

重新生成：`pnpm fixtures`（需要 ffmpeg，可用 `FFMPEG=<路径>` 指定）。

### 2.2 可复现命令

```bash
pnpm typecheck     # tsc --noEmit
pnpm test          # 42 项单测（41 通过 + 1 项按需跳过）
pnpm check:bundle  # vite build + 扫描产物里的 Node 内置模块残留 + 体积报告
pnpm verify        # 以上三步串起来
```

针对真实曲库的实测（默认跳过，需要指向你的音乐目录）：

```powershell
$env:M0_MUSIC_DIR='D:\Music'; pnpm test
```

它会遍历该目录、逐个解析，打印文件数、格式分布、遍历/解析耗时、只读文件头的命中率、
实际读取字节数占比、封面命中数与"推算 3000 首需要多久"。

## 3. 逐项结论与证据

### 3.1 元数据解析：通过

`src/platform/metadata.ts` 用 `parseBuffer` 解析，`src/platform/metadata.test.ts` 锁住行为：

- FLAC：标题 `青花瓷`、艺术家 `周杰伦`、专辑 `我很忙`、音轨号 1、年份 2007、`lossless: true`、时长 2s、封面为 JPEG（校验了 `FF D8` 魔术字节）
- MP3：同样的中文标签、`MPEG 1 Layer 3`、192kbps、封面为 JPEG
- 无标签文件：标题回退为文件名，`titleFromFileName: true`

中文标签不是问题：只要标签是 UTF-8 或 UTF-16（ID3v2.3/2.4 的正常写法），
`music-metadata` 直接解对。**GBK 老标签仍未验证**，见第 5 节。

### 3.2 只用文件头就能解析：通过（本次最有价值的发现）

FLAC 的 STREAMINFO 在文件最开头，Vorbis comment 紧随其后；MP3 的 ID3v2 也在开头。
实测把文件截断到 **前 1KB** 仍然能读出完整的标题、艺术家与封面。

这意味着扫描时不需要读整个文件。实测（31.1MB 的 5 分钟 FLAC）：

| 操作 | 中位耗时 |
| --- | --- |
| `fs` 读整个文件（31.1MB） | 14.7ms |
| `parseFile(整文件)` | 2.3ms |
| `parseBuffer(前 256KB)` | 0.7ms |
| `parseBlob(前 256KB Blob)` | 1.3ms |

两点值得记下来：

1. **`parseFile` 本身是惰性的**，它并不会把整个文件读进来（31MB 文件只用 2.3ms）。
   所以"解析慢"不是问题，**磁盘 I/O 才是**。在冷缓存下，读 256KB 和读 31MB 的差别
   是数量级的，这才是"只读文件头"的真正收益。
2. `parseBlob` 在 Node 里用 Blob 跑通了，与浏览器是同一条代码路径（Blob + ReadableStream），
   所以浏览器侧的行为已被间接验证。

因此 `readMetadata` 采用两级策略，并用**记录读取区间**的方式在测试里锁死：

- 正常情况只读一次文件头（默认 512KB）→ 断言 `reads === [[0, 8192]]`，即没有第二次读
- 头部读不出标题/艺术家/专辑时才回退读整个文件 → 断言 `readStrategy === 'full'` 且读了两次

### 3.3 浏览器产物：通过

产品文档 8 节列的第一个风险是「`music-metadata` 的浏览器可用性与打包体积尚未验证」。
`pnpm check:bundle` 给出可重复的答案：

- **没有任何 `node:` 协议引用**，说明产物可以直接在浏览器里跑，不需要 polyfill
- 体积（`minify: false` 的测量构建）：JS 合计 444KB，其中主 chunk 197KB / gzip 49.5KB；
  其余是按格式拆分的解析器（MP4Parser 40KB、FlacParser 13KB、MpegParser 21KB 等）

> 体积数字是在关闭压缩的测量构建下得到的，正式构建压缩后会明显更小。
> 即便如此，解析器是按需拆分的，首屏不必一次加载全部格式。

### 3.4 目录递归遍历：通过

`src/platform/nodeMusicSource.ts` 实现了与浏览器侧同构的遍历逻辑
（同为 `MusicSource` 接口，复用同一个 `isAudioFileName` / `joinRelativePath`）。
`nodeMusicSource.test.ts` 在临时目录里搭出一棵真实的树验证：

- 递归找出全部音频文件，忽略 `.jpg` / `.txt` 与空目录
- 相对路径统一为 posix 分隔符（`专辑/CD2/plain.mp3`），保证跨平台缓存键一致
- 进度回调单调递增到总数
- 端到端跑通"遍历 → 打开 → 解析"：中文标签、音轨号前缀文件名、无标签回退、损坏文件不中断

### 3.5 不支持格式：需要我们自己判定，不能靠解析报错

实测发现 `music-metadata` 遇到无法解析的内容时抛的是底层错误
（`EndOfStreamError`、`CouldNotDetermineFileTypeError`），**没有干净的"不支持"信号**。

同时它也给出了一个反直觉的好消息：`getSupportedMimeTypes()` 里包含
`audio/ape`、`audio/dsd`、`audio/dsf`、`audio/wavpack`、`audio/musepack`——
也就是说 **APE / DSD / WavPack 读得出标签，只是放不出声音**。

所以 `src/core/audioFormats.ts` 把判定做成两档：

- `decodable`：Chromium 能解码（mp3 / flac / wav / m4a / ogg / opus / webm …）
- `metadata-only`：能读出标题艺术家并展示，但不能播放，并带一句用户可读的说明

并且因为 `.m4a` 里可能装的是 ALAC（Chromium 解不了），判定在解析出 `codec` 之后
还要用 `resolveVerdict` 复核一次。这条正好覆盖了产品文档 3.A.4「明确标记为不支持而非静默失败」。

### 3.6 真实文件实测

工作区里后来出现了两首真实歌曲，于是直接拿它们跑了一遍
（`M0_MUSIC_DIR='D:\轻音播放\新建文件夹' pnpm test`）：

| 文件 | 大小 | 容器 | 读出的标签 | 时长 | 内嵌封面 |
| --- | --- | --- | --- | --- | --- |
| `bôa - Duvet.flac` | 22.0MB | FLAC | BoA / Duvet / Twilight | 203.6s | 无 |
| `Cyberpunk - I Really Want to Stay at Your House.mp3` | 3.8MB | MPEG 1 Layer 3（ID3v2.3） | Cyberpunk / I Really Want… / Edgerunners Soundtrack Vol.1 | 246.7s | 无 |

冒烟结果：遍历 2ms；**只读文件头 2/2**；实际读取 1.0MB，占总体积的 **3.9%**；
中文与带变音符的标签（`bôa`）都正常，无乱码。

两个文件都没有内嵌封面，所以"读到封面 0/2"是**正确结果而非缺陷**——这一点我另外验证过：
直接扫容器结构，FLAC 的元数据块只有 `STREAMINFO(34B) + SEEKTABLE(378B) + VORBIS_COMMENT(87B)
+ PADDING(8145B)`，压根没有 PICTURE 块；MP3 的 ID3v2 标签总长只有 **351 字节**，没有 APIC 帧。

**顺带测出一个比固定头部长度更值得注意的事实**：真实文件的元数据区小得惊人——
FLAC 是 8.6KB，MP3 是 351B，而当前实现固定读 512KB，是所需量的几十倍。

再测不同头部长度对耗时的影响（各 15 次取中位）：

| 头部长度 | FLAC 解析 | MP3 解析 |
| --- | --- | --- |
| 8KB | 0.55ms | 0.76ms |
| 16KB | 0.48ms | 0.84ms |
| 64KB | 0.49ms | 0.76ms |
| 256KB | 0.44ms | 0.72ms |
| 512KB | 0.46ms | 0.61ms |

结论：**解析耗时与头部长度无关**（`parseBuffer` 只走它需要的元数据块，不会扫整个缓冲区），
成本纯粹在磁盘读取上——句柄读 16KB 是 0.17ms，读整个 22MB 文件是 9.71ms（还是走页缓存的情况）。

因此 512KB 是一个"安全但浪费"的取值：对常见文件浪费几十倍 I/O，却又**不能保证**覆盖
超大内嵌封面（封面块排在 512KB 之后时会被静默漏掉，见第 5 节第 3 条）。
按容器结构算准元数据区可以同时解决这两件事，建议放进 M1（见第 7 节）。

> 冒烟里"平均 36.2ms/首"这个数字具有误导性：样本只有 2 个文件，
> 首次调用要加载解析器模块，均值被预热成本主导。稳态解析是上表的 0.5–0.8ms。

## 4. 对产品技术文档的影响

| 文档条目 | 变化 |
| --- | --- |
| 8 节「元数据解析方案」风险 | **消解**。不需要自研解析器 |
| 8 节「大库扫描卡顿」风险 | **大幅降低**。默认只读文件头，实测 31MB 文件只需读 256KB |
| 5.4 节「解析为 CPU 密集操作」 | 结论修正：瓶颈是 I/O 不是 CPU（31MB 文件 `parseFile` 仅 2.3ms，且解析耗时与头部长度无关），Web Worker 仍有用但不再是首要手段 |
| 3.A.4「格式兼容标记」 | 方案明确：扩展名预分类 + codec 复核，两档判定 |
| 3.A.2「内嵌封面」 | **修正一个隐含假设**：真实文件常常压根没有内嵌封面（实测两首都没有），界面必须能优雅处理"无封面" |
| 5.1 节技术栈 | 无需改动，`music-metadata` 保留 |
| 7 节 M0 | 通过，可进入 M1 |

## 5. 仍然未验证的部分

诚实列出 M0 没有覆盖到的，避免误以为"全都验过了"：

1. **真实浏览器里的 `showDirectoryPicker()`**。需要用户手势与真实文件对话框，无法在 CI 里自动化。
   已提供手动验证页：`pnpm dev:m0` 打开 <http://localhost:5174/>
   （File System Access API 要求安全上下文，`file://` 不行）。
   该页面打开时会自动跑一次"内置样本自检"，用打进来的真实 flac/mp3 验证浏览器里的解析结果。
2. **GBK 老标签**。文档 8 节列的"中文标签乱码"风险尚未验证。fixture 是 ffmpeg 写的
   UTF-16 ID3v2.3，两首真实歌曲也是正常编码；只有当标签以 `encoding=0x00` 却塞了 GBK 字节时
   才会乱码，这种情况需要手工构造样本，留给 M1。
3. **超大内嵌封面**。第 3.6 节实测出真实元数据区只有几百字节到几 KB，所以当前 512KB
   的固定头部是"浪费但安全"的；反过来，如果某文件的封面块排在 512KB 之后而标题在头部之内，
   当前逻辑不会回退读整文件，封面会被静默漏掉。这两条都指向同一个修法（见第 7 节）。
4. **真实曲库的规模与乱码率**。目前只跑了 2 个文件，还不能代表数千首的库。
   要更大样本请跑 `M0_MUSIC_DIR=<你的目录> pnpm test`。
5. **播放本身**。M0 只验到元数据，解码播放、MediaSession、PWA 都还没碰。

## 6. 环境备注

- 本机的 `git` 不在 PATH 上，只在 GitHub Desktop 的打包里：
  `%LOCALAPPDATA%\GitHubDesktop\app-3.6.3\resources\app\git\cmd\git.exe`
- 本机没有 `npm`，用 `pnpm`（`node <pnpm.mjs>`）
- 本机 ffmpeg 是精简构建：没有 PNG 编解码器，所以封面样本用 JPEG；MP3 编码器是 `mp3_mf`
  （没有 libmp3lame），因此样本的时长来自 MediaFoundation 写出的头

## 7. 建议的下一步

M0 的结论是"可以做"，没有留下需要返工的阻塞项。M1 开始时建议优先处理两件事：

1. **按容器结构算准元数据区，替掉固定的 512KB 头部**（`core` 层纯逻辑，易测）：
   - FLAC：从 `fLaC` 标记开始逐个走 metadata block 头（每个 4 字节），累加到最后一个块，
     得到元数据区的精确结束位置；实测真实文件只有 8.6KB
   - MP3：ID3v2 的 10 字节头里就有标签长度，实测真实文件只有 351B
   - 其它容器：回退到固定上限
   收益是同时解决第 5 节第 3 条的两面——常见文件的 I/O 降到几十分之一，
   超大内嵌封面也不会再被静默漏掉。
2. **GBK 标签回退**。这是产品文档 8 节里唯一还没被 M0 触及的风险，
   也是老 mp3 上最容易真实影响观感的问题。做法：检测到乱码特征时把字符串按
   latin1 还原成字节，再用 `TextDecoder('gbk')` 重解码（Node 与 Chromium 都支持）。

再往后，M1 的落点才是产品文档原本定义的"曲库接入"：把 `MusicSource` 的浏览器实现
（`m0/browserMusicSource.ts` 已验证过形态）正式并入 `src/platform`，接上 IndexedDB 缓存
与扫描进度。`demo/` 里的界面可以直接迁到 React + Zustand 上。
