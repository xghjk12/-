## 1. 怎么跑自动化

前置：仓库根目录、`pnpm build` 已跑过、**正在运行的轻音播放已完全退出**
（origin 是固定端口 `53140`，不换端口；脚本启动前会先探测并给出明确提示）。

```powershell
node desktop/verify.mjs
# 报告：artifacts/desktop/verify.json（assertionSummary 分「沿用上一期 / 本期新增」）
# 截图：artifacts/desktop/verify-library.png / verify-lyrics.png /
#       verify-after-hide.png / verify-desktop-hidden.png（隐藏期间的全屏图）/
#       verify-lyrics-fill.png（假工具补完歌词后的面板）
```

脚本行为（t7 扩展后）：

- 用 `playwright-core` 的 `_electron.launch()` 驱动**真入口** `desktop/main.js`
  （不是探针、不是浏览器预览）；启动参数 `--no-sandbox`。
- 共 **9 次真实启动**、4 个隔离 profile，全部**每次清空**，不碰用户真实曲库：
  `userdata-verify`（t3 四条的 4 首内置样本）、`userdata-verify-lyrics`（补歌词三幕）、
  `userdata-verify-window`（窗口状态四轮）。
- 补歌词用 `desktop/tools/fake-fill-lyrics.ps1` 往一个临时曲库目录写确定内容的 `.lrc`，
  **全程不联网、不碰真实 LyricFlow**；曲库走真实原生目录选择（`driveFolderDialog.ps1`）。
- 失败时不会只甩一句断言：会额外打印 `url / readyState / .app 是否挂载 / rows / 是否空状态 /
  selfTest 结论`，用来区分「首帧还没布局」和「真错了」。
- 连续多次启动 Electron 时 Playwright 的 CDP 连接偶尔会 ECONNRESET（主进程已正常起来），
  脚本会重试最多 3 次并把每次失败记进 `mainLog`——不装作没发生。
- 判定项逐条打印 ✔/✖ 与实测值；任何一条失败 → 退出码 1 并写进 `verify.json.problems`。
- 报告里 `assertions.inherited[]` / `assertions.added[]` 明确列出每组断言（含通过与否），
  复核的人据此核对有没有退化。

## 2. 自动化到底断言了什么（为什么这些断言不是空转）

### 2.1 窗口 + 行数

顺序是刻意的：`waitForSelector('.row, .empty')` → 等 `rows >= 4` → 再让两帧 →
最后才在 DOM 里数。**只等 `domcontentloaded` 就数会量到 rows=0**（t1 踩过）。

另外 `?selftest=1` 的内置自检会临时塞 500 首合成曲目、量完再还原；脚本会先等
`<html data-self-test>` 出现（自检跑完）再导入样本，避免量到那一瞬间的合成列表。
这就是「虚拟化偶发 false / 行数偶发不对」的根因，不是产品缺陷。

### 2.2 真实播放

不是看 store 的 `playing` 布尔就完事——同时断言 **audio 元素**：

- `paused === false`
- `currentTime > 0.05` 且在后续采样里持续增长
- `currentSrc` 非空（`blob:http://127.0.0.1:53140/…`，说明真的解码了样本）
- 当前曲目路径是 `plain.mp3`（双击的那一行）

### 2.3 歌词面板

走**真实侧栏入口**（点「歌词」），断言 `.drawer .lyrics`、不是「还没有歌词」占位、
`plain.lrc` 的 3 行文本都渲染、标题是当前曲目。

> 注：`?selftest=1` 会往页面塞一个自检结果浮层 `#selfTestResult`，它会拦截鼠标事件
> （实测把抽屉关闭按钮盖住了）。脚本量完自检结论后把这个节点摘掉——真实用户入口
> 没有这个节点，摘掉之后的点击与截图才和用户看到的一致。

### 2.4 隐藏窗口后音乐继续（核心）

1. 切到**列表循环**（内置样本 1–2 秒，不切循环队列 8 秒就放完了，
   会把「还在放」误判成失败）。
2. 双击列表第一行开始播，记录基线。
3. 调 `__qingyinDesktopShell.hideMainWindow()`——**托盘「隐藏窗口」菜单项调用的就是它**，
   不是绕过产品代码的 `win.hide()`。
4. 断言主进程 `isVisible() === false`、窗口对象还在、`isQuitting === false`、
   托盘菜单文案翻成「显示窗口」。
5. 3 秒内每 150ms 采样 `currentTime`；同时用 `snapshotDesktop.ps1` 做一次
   EnumWindows 转储，确认屏幕上真的没有轻音播放窗口。
6. 判定：`paused` 一次都没有 true、`playing` 一直 true、累计正增量 ≥ 1 秒
   **或**发生自动切歌（= 上一首自然播完，也是播放没停的硬证据）。
7. 再从托盘显示回来，断言窗口可见且仍在播、位置继续走。
8. **反证**：暂停后同一套采样必须量不到前进（实测 delta=0），否则说明测的不是播放进度。

为什么不用「首尾两个 `positionSec` 比大小」：样本只有 1–2 秒，列表循环下会不断切歌，
位置归零会看起来像「没动」。正确算法是同曲累加正增量 + 统计切歌次数（见
`summarizeSamples()`）。

### 2.5 两个实测到的环境事实（别再踩）

1. **`BrowserWindow.hide()` 不会把 `document.visibilityState` 变成 `hidden`**。
   本机 21 次采样全是 `visible`。所以**不能**用页面可见性判断窗口是否隐藏，
   判据用主进程 `isVisible()` + OS 层 EnumWindows。
2. CDP/Playwright 的 `page.evaluate()` 在窗口隐藏时照常可用；音频在渲染进程里继续跑，
   所以隐藏期间可以直接读 `currentTime`，不需要任何注入。

### 2.6 补歌词链路（t7 新增，假工具、绝不联网）

用 `desktop/tools/fake-fill-lyrics.ps1` 替换 `settings.lyricsToolPath`，它只做一件事：
在曲库目录里挑一首没有同名 `.lrc` 的音频，写一个内容确定的 3 行歌词，退出 0。
链路全部走真实路径：托盘「补歌词…」的同一个函数 → 主进程 `spawn powershell` →
状态推送 → 渲染进程 `rescanLyrics()` → 认领 + 通知。**不碰真实 LyricFlow、不联网。**

- **成功**：触发快照就是 `running`（不是等轮询才看到），终态 `done/exit 0`；
  磁盘上 `.lrc` 94B；认领记录 `source=sidecar` 且文本含「假工具第一句」；
  UI 通知抓到 **`歌词扫描：新认领 1`**（正则取数，断言 ≥1）+ `补歌词完成，已重新扫描歌词`；
  按 `y` 打开面板看到 3 行；**全程 `audio.paused=false`、`playing=true`**（第一不变式）。
- **失败 8a（路径不存在）**：`lyricsToolPath` 指向一个不存在文件。实现语义是
  `lyricsIpc.currentScriptPath()` 回退内置 `fill-lyrics.ps1`（README §9 有说明），
  所以断言的是：仍然启动（不是静默）、`scriptPath` 确实回退、终态 `failed`、
  日志尾可读。为了让失败发生在启动 python 之前（**绝不联网**），故意把
  `musicFolderPath` 指向一个**文件**，内置脚本第一道 `-PathType Container` 校验就会
  `exit 3`：实测日志尾 = `MUSIC_PATH 不是有效目录：…\tests\fixtures\plain.mp3`。
- **失败 8b（工具内部失败）**：用一个存在、但 `exit 5` 并往 stderr 写可读错误的脚本。
  断言 `failed + exitCode 5`、日志尾含 `VERIFY-FAIL-TOOL`、UI 弹出
  「补歌词失败（…）」——**不许静默**。
- **取消**：慢工具里拉一个带唯一 marker 的子进程睡 90 秒 → 渲染进程走 preload 的
  `lyrics.cancel()` → 终态 `cancelled`（不是 failed，`error=null`、有 `finishedAt`）、
  菜单「补歌词…（上次已取消）」、UI「已取消补歌词」、**进程表里 marker 进程 0 个**
  （`taskkill /T` 杀整棵树）、曲库目录里没有写出 `.lrc`。

> 「每条都证明观察到了变化」：成功链路有 `running→done` 的状态序列 + 磁盘文件 + 认领记录
> 三份独立读数；失败链路同时有主进程终态 + 日志尾 + UI 通知；取消链路同时有 IPC 返回值 +
> 主进程终态 + 菜单文案 + 进程表计数 + 文件不存在。

### 2.7 托盘播放控制（t7 新增，全程窗口隐藏）

命令走 `__qingyinDesktopShell.playbackCommand(type)`——托盘菜单项 click 调用的同一个函数，
不是另开的后门。先把播放模式锁成单曲循环（1–2 秒样本不会自动切歌干扰下标断言），
然后**隐藏窗口**，再依次发命令，每一步同时读三处：

| 命令 | 渲染进程 | 主进程上报 | 托盘菜单 |
| --- | --- | --- | --- |
| play-pause | `audio.paused false→true` | `playing=false` | 「播放」 |
| play-pause | `true→false` | `playing=true` | 「暂停」 |
| next | `currentIndex 3→0`（队列回绕） | 同一个下标 | — |
| prev | `0→3`（回到切歌前那首） | 同一个下标 | — |

另外断言：队列长度 4、曲目顺序不变（没搞乱）、非法命令 `quit` 被白名单拒绝、
整组命令期间 `windowVisible=false && windowExists=true`、显示回来后仍在播。
`next` 的期望值按 `(index+1) % queueLength` 算，不是只断言「变了」——避免把自动切歌
误认成命令生效。

### 2.8 窗口状态记忆（t7 新增，四次真实启动）

全部用同一个隔离 profile，`settings.json` 由 node 侧直接读（不靠主进程自证）：

1. **首次启动**：无存档、`source=default`、窗口在屏内；`setBounds({60,40,1180,704})`
   → 等防抖（600ms）→ 磁盘里就是这组值、写盘计数 `writes=1`；
   最大化后存档 `maximized=true`，且宽高是 `getNormalBounds`（1180×704）而不是屏幕尺寸
   （屏幕 bounds `1552×840`）。托盘退出 `exit 0` 后最大化状态仍在。
2. **重启**：`source=saved`、`isMaximized()=true`；还原后回到 `{60,40,1184,704}`
   （容差 40px，Windows 边框/DPI 会漂）；换到 `{220,160,1024,600}` → 写盘更新、退出。
3. **屏幕外（副屏 x=3000，本机只有一块屏）**：`source=default`，`reason` 明确写
   「不在任何屏幕的工作区里（显示器被拔掉？）」；窗口可见且在屏内；退出写回屏内几何。
4. **脏坐标（x=99999）**：`sanitizeWindowState` 直接丢弃 → `saved=null`、`source=default`；
   窗口出现在屏内；退出后存档仍是屏内几何（没有把脏坐标写回去）。

### 2.9 一条实现语义，复核时别误判

**自定义 `lyricsToolPath` 不存在时，实现会静默回退内置脚本**（`lyricsIpc.js` 的
`currentScriptPath()`：`custom && fs.existsSync(custom) ? custom : builtInScriptPath`）。
t7 的要求是「指向不存在的脚本 → 状态必须 failed」。这两者并不冲突：回退后的内置脚本
同样以 `failed` + 可读错误收场（8a 已验证），但**错误内容说的是音乐目录不合法，
不是"你的工具路径没了"**。如果产品希望"自定义路径失效"直接报错而不是回退，
这是一个需要产品决策的小改动（不属于 t7 验证脚本能改的范围）——已作为观察项记在报告里。

## 3. 人工清单（四项，每项都写清「怎么看 / 预期」）

> 建议按顺序做，全程约 5 分钟（第 2 项需要重启电脑，另算）。

### 3.1 托盘图标与菜单是否出现、是否可用

**怎么看**

1. 仓库根目录启动：`powershell -ExecutionPolicy Bypass -File desktop/start.ps1`
2. 看任务栏右下角通知区域；Win11 默认折叠，点「^」展开。
3. 鼠标悬停图标 1 秒看 tooltip；**左键单击**图标；**右键单击**图标。

**预期**

- 图标是轻音播放的图标（不是空白、不是默认 Electron 图标），tooltip 为 `轻音播放 v0.1.0`。
- 左键单击：窗口在「显示 / 隐藏」之间切换（隐藏时音乐不能停）。
- 右键菜单（t7 之后共 10 项，分隔条分组）：
  `隐藏窗口`/`显示窗口`（随状态换向）→ `播放`/`暂停`（随播放状态换向）、`上一首`、`下一首`
  → `补歌词…`（随工具状态换向：运行中/上次成功/上次失败/上次已取消）、`指定音乐文件夹…`、
  `选择补歌词工具…` → `开机自启`（可勾选）→ `当前 v0.1.0 · 检查更新下一期提供`（灰色禁用）
  → `退出`。
- 曲库为空时 `播放/暂停、上一首、下一首` 三项是**灰色**的（没有当前曲目可控制）。
- 窗口隐藏时菜单第一项变成「显示窗口」；点它窗口回来且正在放的歌没断。

**不符合时记什么**：Windows 版本、托盘是否被折叠、图标是否被裁切/空白；
以及 `__qingyinDesktopShell.readState()` 里 `trayCreated` / `menu` 的实际值（t2 自动化里有）。

### 3.2 开机自启是否真的生效（必须在**重启电脑后**看）

**怎么看**

1. 右键托盘 → 勾选「开机自启」。
2. 立刻先验写入：任务管理器 → 「启动」选项卡（Win11：设置 → 应用 → 启动）→
   找到 `qingyin-player`，状态应为「已启用」；
   或命令行：`reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v qingyin-player`（应有值）。
3. **完全退出**轻音播放（托盘 → 退出，确认任务管理器里没有 electron 进程）。
4. 重启电脑（或注销再登录），**不要手动点图标**，等 10–20 秒。
5. 反向验证：托盘取消勾选 → `reg query` 应查不到该项 → 再重启，不应自启。

**预期**

- 登录后窗口自动出现、托盘图标自动出现；曲库和上次播放位置还在（同一个 userData）。
- 取消勾选后，Run 项消失，重启不再自启。

**注意**

- 未打包形态下，自启命令是 `electron.exe <仓库>\desktop --no-sandbox`（见
  `__qingyinDesktopShell.readState().loginItemCommand`），不是 exe 安装包。
- 若任务管理器显示「已禁用」，说明 StartupApproved 被系统改过：手动「启用」一次再复测。
- 在 DSH 沙箱里切开关时，Electron 子进程写注册表会被降权（README §8）——**以真机手动
  启动的实例为准**，任务管理器/`reg query` 是最终裁判。

**不符合时记什么**：`reg query` 两条（Run / StartupApproved）的原始输出、任务管理器状态、
是否被杀软/优化软件拦截、登录后手动启动是否正常。

### 3.3 窗口隐藏时**系统媒体键**是否仍响应

**怎么看**

1. 播放一首歌（窗口可见）。
2. 点窗口右上角 X（关到托盘）或托盘菜单「隐藏窗口」——确认窗口消失、音乐继续。
3. 按键盘上的媒体键：**播放/暂停**、**下一首**、**上一首**
   （笔记本可能是 `Fn+F*`；耳机线控/蓝牙耳机按钮也算）。
4. 观察 Windows 的媒体浮层（按音量键时左上角/左下角出现的卡片）是否显示当前曲名、
   歌手、封面，以及按键后是否切歌。

**预期**

- 播放/暂停立即生效（音乐停/继续），上一首/下一首切歌；
- 系统媒体浮层显示「轻音播放」的当前曲目；窗口始终隐藏，音乐不断。
- 再显示窗口时，界面状态与刚才按键的结果一致（例如按了下一首，界面已在下一首）。

**不符合时记什么**：键盘型号/连接方式（有线、蓝牙、接收器）、是否有其它播放器
（网易云/Spotify/浏览器标签）在后台抢占媒体键、Windows 版本。
这条依赖 Chromium MediaSession 与 Windows SMTC 的集成，属于系统集成风险；
若 MediaSession 未被系统接管，应作为缺陷单独立项，而不是混进「关窗继续播」的结论。

### 3.4 托盘「退出」是否真能退出

**怎么看**

1. 先关窗到托盘（窗口消失、音乐还在放）。
2. 右键托盘图标 → 「退出」。
3. 立刻看：托盘图标是否消失、音乐是否停；
   打开任务管理器 → 「详细信息」，搜 `electron` / `轻音`，应无残留；
   命令行：`netstat -ano | findstr :53140` 应无输出。
4. 再执行一次 `desktop/start.ps1`：应正常打开（不能弹「端口 53140 已被占用」）。

**预期**

- 音乐立即停止，托盘图标消失，进程退出（退出码 0），53140 端口释放；
- 重新启动一次成功，曲库与上次进度还在。

**不符合时记什么**：任务管理器里残留进程的 PID/命令行、端口占用者 PID
（`netstat -ano | findstr :53140`），以及是否属于 README §5 坑 9 的僵尸进程。

## 4. 本次没覆盖 / 已知边界

- **打包版（安装包）未验证**：本期只在仓库目录形态（`electron desktop`）跑通；
  自启命令、图标路径、`app.isPackaged` 分支都要在打包后复测。
- **系统媒体键、重启自启没有自动化**：前者要真人按硬件键，后者要真重启；已在第 3 节给出手工步骤。
- `--no-sandbox` 是安全降级（README §5 坑 2），换干净机器必须复测沙箱能否打开。
- 只在本机 Windows 验证；macOS/Linux 的自启实现走的是另一条分支（`app.setLoginItemSettings`），未测。
- 内置自检的「虚拟化」一项在 Electron 首帧仍可能偶发 false（web 端同一份 dist 全过）；
  `verify.mjs` 会等自检跑完再量，若仍失败只记警告并打印明细，不拿它当桌面端四条判定的替罪羊。
- **补歌词自动化只用假工具**：真实 LyricFlow 会联网（`api.lrc.cx`），自动化刻意不跑它；
  真实链路见第 6.1 节人工步骤。假工具的曲库是 `artifacts/desktop/verify-lyrics-music`
  （从 `tests/fixtures/sample-cn.mp3` 复制），每次重建，不碰用户曲库。
- **失败路径的语义差异**：`lyricsToolPath` 不存在时实现会回退内置脚本（第 2.9 节），
  所以「不存在路径」这条断言的是"不静默 + 最终 failed + 可读错误"，而不是"报错说工具文件没了"。
  为杜绝联网，8a 故意让内置脚本在"音乐目录不是目录"这一步失败（exit 3）。
- **托盘菜单是 OS 层控件**：自动化只能读 `readState().menu` 的 label/enabled 数据，
  原生渲染观感（对齐、主题对比度、是否被系统截断）属于第 6.2 节人工项。
- **多显示器拔插无法真机自动化**：本机只有一块屏，脚本用 `x=3000`（模拟拔掉的副屏）和
  `x=99999`（脏坐标）覆盖回退逻辑；真实的拔插顺序见第 6.3 节。
- 全脚本 9 次启动约 45 秒；首次运行若撞上 Playwright CDP 抖动会自动重试 3 次，
  重试记录在报告 `mainLog` 里（不是产品错误）。

## 5. t6 追加的人工清单（两项）

自动化已经把可判定的部分钉死了（`desktop/checkTrayPlayback.js`、`desktop/checkWindowState.js`，
判定细节见 README §3.8.3）。下面两项是**只有真人能验**的部分：菜单弹出的观感、
以及"用鼠标拖"和"用 `setBounds` 摆"的差别。

### 5.1 托盘三键的手感与文案

- **怎么看**：随便放一首歌 → 点窗口 X 关到托盘（音乐不该停）→ 右键托盘图标，
  依次点「暂停」「播放」「下一首」「上一首」，每点一次都重新打开菜单看文案；
  最后从托盘「显示窗口」，核对界面上的曲名/进度条与刚才听到的是否一致。
- **预期**：
  - 暂停后菜单第一行变成「播放」，声音立刻停；播放后变回「暂停」；
  - 「下一首/上一首」真的换曲（曲名、封面、歌词面板都跟着换），且**换完还在放**；
  - 有当前曲目时三项都不是灰的；**曲库为空时三项都应该是灰的**（这是刻意的：
    点了没反应比灰掉更糟）；
  - 点菜单到听见变化之间没有可感知的延迟（同进程 IPC，应该 <50ms）。
- **不符合时记什么**：菜单截图（要能看出文案）+ `artifacts/desktop/tray-playback-check.json`
  + 主进程控制台里有没有 `[desktop] 托盘播放命令未送达：…`（这句是主进程发的兜底日志，
  出现即说明窗口没了或 type 不在白名单里）。
- **为什么自动化不够**：脚本断言的是 `audio.paused` / `currentIndex` / 菜单 `label`，
  它测不到原生菜单的**渲染观感**（图标对齐、分隔条位置、文案是否被截断），
  也测不到真人右键时菜单出现在哪块屏幕上。

### 5.2 窗口位置 / 尺寸 / 最大化的记忆（真人拖动版）

- **怎么看**：
  1. 用鼠标把窗口拖到一个别扭的位置、拉成不规则大小 → 托盘「退出」→ 重新启动
     （`powershell -ExecutionPolicy Bypass -File desktop/start.ps1`）→ 看回没回到刚才的样子；
  2. 最大化 → 退出 → 重启：应该直接是最大化；点还原按钮后应该是**退出前的普通尺寸**，
     不是整块屏幕的尺寸；
  3. 只点 X 关到托盘，再从托盘「显示窗口」：窗口位置不该有任何变化（隐藏不写盘、不重定位）；
  4. 屏幕外回退（不用真拔显示器）：编辑 `artifacts/desktop/userdata/settings.json`
     （坑 3 的降级路径；正常机器是 `%APPDATA%\qingyin-player\settings.json`），
     把 `windowState` 的 `x`/`y` 改成 `3000`/`200`（模拟拔掉的副屏）或 `-32000`/`-32000`，
     重启 → 窗口必须出现在主屏正中，而不是"进程在跑但看不见窗口"。
- **预期**：1–3 全部原样恢复；4 回退到主屏居中默认尺寸，且启动日志里有
  `[desktop] 窗口几何来源 = default（已保存的位置 … 不在任何屏幕的工作区里（显示器被拔掉？），回退到主屏居中）`。
- **不符合时记什么**：`settings.json` 里 `windowState` 的实际内容、启动日志那一行、
  显示器分辨率与缩放比例（`Get-CimInstance Win32_VideoController | Select-Object CurrentHorizontalResolution, CurrentVerticalResolution`）。
  缩放不是 100% 时几何会有十几像素的漂移，那是坑 13 记的既有行为，不算失败。
- **已知边界**：防抖窗口 600ms，进程被强杀（任务管理器结束进程 / 断电）时最后一次拖动可能丢，
  下次启动回到上上次的位置——这是设计取舍（README §7.11），不是 bug。

## 6. t7 追加的人工清单（三项）

自动化已经用**假工具**把补歌词链路（成功/失败/取消）、托盘播放控制、窗口状态记忆全部钉死
（判定细节见第 2.6–2.8 节）。下面三项是自动化**替不了**的：真实外部工具、原生菜单观感、
真实拔插显示器。

### 6.1 真实 LyricFlow 跑一次（含 venv 缺失时的引导文案）

> 自动化只用假工具，**不联网**；真实工具这一步必须人来做，建议在自己的曲库上跑。

- **怎么看**：
  1. 确认 `artifacts/lyricflow/.venv/Scripts/python.exe` 存在（不存在时的引导文案见下一条）；
  2. 启动 `powershell -ExecutionPolicy Bypass -File desktop/start.ps1`，选好音乐文件夹；
  3. 右键托盘 →「补歌词…」；立刻再打开菜单，第一项应显示「补歌词…（运行中）」；
  4. 等它跑：菜单最终变成「补歌词…（上次成功）」或「（上次失败）」；
  5. 回到窗口（托盘「显示窗口」）→ 看右下角通知：应有「补歌词完成，已重新扫描歌词」+
     「歌词扫描：新认领 N、更新 N、未变化 N」；打开歌词面板，新补的那首歌应能看到歌词；
  6. **venv 缺失的引导**：临时把 `artifacts/lyricflow` 改名（或换一台没装过的机器）→
     点「补歌词…」→ 等它失败 → 看 UI 提示 / 日志尾是否给出**可照做的安装步骤**
     （取源码 → `python -m venv .venv` → `pip install httpx mutagen` → 再点一次），
     而不是一句冷冰冰的「失败」。
- **预期**：状态文案按 running → done/failed 换向；通知里 N≥1（新歌词确实被认领）；
  歌词面板能看到新内容；**补歌词全程音乐不停、窗口隐藏也照常收状态**；
  venv 缺失时提示里包含可复制的安装命令与路径。
- **不符合时记什么**：UI 通知原文、`artifacts/desktop` 之外没有报告（真实工具不经过
  verify.mjs），所以记 `artifacts/lyricflow` 是否存在、托盘菜单文案、以及主进程日志里的
  `[desktop]` 行；再附 `settings.json` 的 `lyricsToolPath` / `musicFolderPath`。
- **注意**：真实工具会访问 `https://api.lrc.cx`（README 的实测参数），公司网络/代理下失败
  属于环境问题；先把网络排除再判产品。

### 6.2 托盘菜单文案是否随播放状态变化（原生菜单观感）

- **怎么看**：
  1. 播一首歌 → 关窗到托盘（音乐继续）；
  2. 右键托盘：`播放/暂停` 这一项此刻应是「**暂停**」；`上一首/下一首` 是可点的黑色文字；
  3. 点「暂停」→ 重新右键：文案变成「**播放**」；再点一次 → 又变回「暂停」；
  4. 曲库为空（新 profile / 还没导入）时再看：三项都应是**灰色**不可点。
- **预期**：文案与当前播放状态一致（播放中=「暂停」）、点击后 1 秒内声音与文案都变、
  空曲库三项灰掉；菜单里没有重复项、分隔条位置正常、中文没有被截断。
- **不符合时记什么**：菜单截图（能看清文案与灰/亮）、`artifacts/desktop/verify.json`
  里 `trayControlPause/Play` 的读数（自动化已证明状态通道是通的，若这里不对，
  问题在原生菜单渲染或点击接线）；主进程日志里搜 `托盘播放命令未送达`。
- **为什么自动化不够**：脚本读的是 `readState().menu` 里的 `label` 数据，
  看不到原生菜单的实际渲染（对齐、字号、是否被系统主题吃掉对比度）。

### 6.3 多显示器拔插后窗口是否回到屏幕内

- **怎么看**：
  1. 接上副屏（或投屏/扩展屏），把窗口拖到副屏上，托盘「退出」；
  2. **拔掉副屏**，重新启动 → 窗口应出现在主屏中央（默认尺寸），而不是"进程在跑但看不见"；
  3. 再插回副屏、启动 → 这次沿用上次存档（副屏还在的话）；把窗口拖回主屏、退出、再启动，
     应回到主屏的位置；
  4. 启动日志里应有一行 `[desktop] 窗口几何来源 = default（已保存的位置 … 不在任何屏幕的
     工作区里（显示器被拔掉？），回退到主屏居中）`。
- **预期**：拔屏后一定能在主屏看到窗口（不是坐标 -32000 的隐形窗口）；插回后几何按存档恢复；
  缩放比例不是 100% 时位置可能差十几像素（README 坑 13 的既有行为，不算失败）。
- **不符合时记什么**：显示器数量与工作区（`screen.getAllDisplays()` 或
  `Get-CimInstance Win32_VideoController`）、`settings.json` 的 `windowState`、
  启动日志的「窗口几何来源」那一行。
- **为什么自动化不够**：本机只有一块屏，脚本只能模拟"存档坐标落在不存在的屏幕上"
  （x=3000 / x=99999，已自动化），**真实的拔插事件顺序**只能人来做。
